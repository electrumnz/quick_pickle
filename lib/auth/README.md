# Admin authentication

The door to the whole business. One password, held to the standard a single
password has to be held to when it is the only thing there.

## What was asked for, and what was built

The founder asked for a discreet link in the site footer opening a login with a
**password field only** — no username, no email — and said, knowingly, that
hardening beyond a password comes later. That is exactly what is here.

"Later" is the part that needed designing. Everything below is arranged so that
adding a passkey or a TOTP code is one new file and one array entry, not a
rewrite of the sign-in flow.

## The shape of it

```
lib/auth/
  config.ts             every constant and every environment read, in one place
  clock.ts              time and sleeping as injectable ports
  login.ts              the sign-in flow, HTTP-free and fully testable
  session.ts            sealed cookie + revocable row
  csrf.ts               sealed double-submit tokens
  throttle.ts           per-IP and global budgets, escalating delay then lockout
  audit.ts              what goes in audit_log
  server.ts             what the admin feature pages call
  runtime.ts            the only file that reads process.env or opens a pool
  crypto/               argon2id, constant-time compare, AES-GCM sealing
  factors/              the second-factor seam
  http/                 route handlers, the proxy decision, cookie serialisation
  scripts/              hash-password, new-session-secret, unlock
  evidence/             machine-generated proof, regenerated by the test suite
proxy.ts                the gate (Next 16's replacement for middleware.ts)
app/(admin)/login/      the page and the two route handlers
components/auth/        the footer link and the sign-out form
supabase/migrations/20260101000600_auth.sql
                        the durable throttle table and its atomic helpers
```

## The decisions, and why

**argon2id, 19 MiB, t=2, p=1.** OWASP's second recommended configuration.
Memory-hard, so a GPU farm cannot parallelise its way through the keyspace the
way it can with bcrypt or a plain SHA. This costs roughly 85 ms per verification
and that cost is the point: it is what makes a human-chosen password survivable
against an offline attack on a leaked hash. Do not trim it for latency.

**The hash lives in `ADMIN_PASSWORD_HASH`, never in the database.** A dump of
the Supabase project must not contain anything that can be cracked back into the
front-door password.

**Verification recomputes and compares in constant time.** `hash-wasm` ships an
`argon2Verify`, and it is deliberately not used: this package does not take on
faith that somebody else's comparison is constant time. The stored parameters
and salt are re-applied, the digest is recomputed, and
`timingSafeEqualBytes` does the comparison with no early return. The same
function compares CSRF tokens and session token digests.

**The session is two things.** A cookie sealed with AES-256-GCM under an
HKDF-derived, purpose-scoped key — encrypted, not merely signed, so its contents
cannot be read client-side and its authentication tag makes forgery a dead end.
And a row in `admin_sessions`, so a session can be ended from the other side.
A cookie alone is not revocable, and "sign out everywhere" has to mean
something. The row stores only the SHA-256 of the bearer token.

**`__Host-` prefix, HttpOnly, Secure, SameSite=Strict, Path=/, no Domain.**
The prefix is enforced in `http/cookies.ts` rather than assumed: a future change
that drops `Secure` throws instead of silently shipping a cookie a sibling
subdomain can overwrite. Both Chrome and Firefox treat `http://localhost` as a
secure context, so this holds in local development too — there is no relaxed
development variant to forget about.

**30-minute idle window with sliding renewal, 12-hour absolute ceiling.**
The window only moves once a session is five minutes stale, so browsing the
admin does not mean a database write per page view.

**The throttle is a table, not a Map.** On Vercel, module scope dies with the
container. An in-memory counter would reset on every cold start, and an attacker
who can provoke cold starts would have an unlimited budget. `public.admin_auth_throttle`
holds it, and `admin_auth_register_attempt()` does read-decide-write inside one
statement so two concurrent attempts cannot interleave.

**Two budgets, per-IP and global.** Per-IP catches the obvious script. Global
catches the same script spread across a botnet, or one spoofing
`X-Forwarded-For` to land in a fresh bucket every request — which a per-IP limit
alone cannot see at all.

**Escalating delay, then a hard lockout that doubles.** Three free attempts,
then 1s, 2s, 4s, 8s… capped at 30s; at eight consecutive failures the address is
shut out for 15 minutes, and each subsequent lockout doubles up to a day.
A locked-out attacker hammering the door keeps digging: the counter climbs, but
they cannot reset their own `lock_count`.

**A fixed response-time floor on every outcome.** Internally the paths differ by
about 85 ms — a wrong password hashes, a lockout refuses before hashing. Every
response is padded to 400 ms, so from outside they are indistinguishable and the
lockout state cannot be read off a stopwatch. See
`evidence/response-timing.txt`: 1 ms between medians.

**Refusing before hashing is deliberate.** A locked-out request must not cost
19 MiB and 85 ms of server CPU, or the lockout becomes a CPU-exhaustion
amplifier rather than a defence. The floor is what makes that safe to do.

**One message for every failure.** Wrong password, stale token, hard lockout —
identical status, identical destination, identical body, identical timing. The
second sentence of the message ("Repeated failures temporarily disable sign in")
is constant, so the founder knows the rule exists without an attacker learning
whether it has engaged. The reason is in `audit_log`, where she can read it and
an attacker cannot.

**Origin and CSRF failures are audited but do not spend throttle budget.**
Neither can ever become a successful guess — a cross-site POST arrives without
cookies, and an attacker's own client can always fetch a fresh CSRF token — so
counting them buys nothing, while handing any website on the internet a way to
lock the founder out by making her browser POST here.

**No username means no user enumeration.** There is nothing to submit that could
tell an attacker an account exists. That absence is load-bearing; do not add an
email field "for convenience".

**The password is never logged.** Not on the happy path, not in an error, not in
a stack trace. `verifyPassword` catches the primitive's own exceptions rather
than letting one propagate with the password on the stack, and the hash-password
script reads from stdin because a command-line argument lands in shell history
and in every user's `ps` output.

### The trade-off worth knowing about

The global lockout means a determined attacker can hold the front door shut for
a few minutes at a time — starting at five, escalating to at most an hour. That
is the price of having a global budget, and the alternative (per-IP only) is
defeated by a single spoofed header. `npm run auth:unlock` clears it, and it
needs database credentials to run, so it is not a lever anyone on the internet
can pull.

## The second-factor seam

`factors/types.ts` defines `AuthFactor`: `isEnrolled()`, `challenge()`,
`verify()`. `factors/registry.ts` holds the configured chain and `runFactorChain`
walks it on **every** sign-in, in production, today. The only registered factor
is `NoopSecondFactor`, which is enrolled for nobody — so the password alone opens
the door, exactly as asked, while the machinery around it is a live code path
rather than a comment saying "add 2FA here".

To add a passkey:

1. Write `PasskeyFactor implements AuthFactor`.
2. Add it to `REGISTERED_FACTORS`.

Nothing else changes. Not `login.ts`, not the route handler, not the session
layer, not the throttle, and not the login form — a challenging factor declares
its own fields and the form renders them.

`tests/auth/factors.test.ts` proves this by doing it: `StubTotpFactor` is written
exactly as a real factor would be, registered through the same array, and the
password stops being sufficient the moment it is. No production file is modified
or mocked to make those tests pass.

## Two layers, on purpose

`proxy.ts` turns an unauthenticated visitor away before the renderer sees the
request — that is what makes "no flash of admin content" structural rather than a
CSS trick. `requireAdminSession()` in `server.ts` checks again inside the render.
Next's own documentation warns that a matcher change, or a Server Function moving
to an uncovered route, can silently remove proxy coverage. So the door is checked
at the door and again at the desk, and both checks are full ones — sealed cookie
opened, row loaded, revocation and expiry honoured.

Both fail closed. If the database is unreachable, the visitor is redirected to
the login page rather than let through: an admin surface that opens when the
database is down is not a surface the database is protecting.

## For the unit building the admin dashboard

Three things:

```tsx
// At the top of every admin page and every admin server action:
const { session, csrfToken } = await requireAdminSession();

// In any form that changes something:
<input type="hidden" name={ADMIN_CSRF_FIELD_NAME} value={csrfToken} />;

// At the top of any handler that receives one:
await assertAdminCsrf(submittedToken); // throws CsrfError -> answer 403
```

And `<AdminSignOutForm csrfToken={csrfToken} />` from `components/auth/` for
sign-out, with `everywhere` for the lost-laptop case.

## Environment

| Variable                    | Required | What it is                                                                                  |
| --------------------------- | -------- | ------------------------------------------------------------------------------------------- |
| `ADMIN_PASSWORD_HASH`       | yes      | argon2id PHC string. `npm run auth:hash-password`                                           |
| `ADMIN_SESSION_SECRET`      | yes      | 32+ random bytes, base64. `npm run auth:new-session-secret`. Rotating it signs everyone out |
| `SUPABASE_DB_URL`           | yes      | Postgres connection string. Without it the gate fails closed                                |
| `ADMIN_OPERATOR_EMAIL`      | no       | Email on the founder's `operators` row. Default `owner@halfsour.co.nz`                      |
| `ADMIN_OPERATOR_NAME`       | no       | Display name on that row                                                                    |
| `ADMIN_TRUST_PROXY_HEADERS` | no       | Believe forwarded-for headers. Defaults to true in production and on Vercel                 |

### Changing the password

```
npm run auth:hash-password
```

Prompts twice with echo off (or reads stdin), prints the hash and nothing else.
Paste it into the Vercel project's environment as `ADMIN_PASSWORD_HASH`. It takes
effect on the next deploy; existing sessions survive, because they are sealed
under `ADMIN_SESSION_SECRET`, not under the password. To end them too, rotate the
session secret as well.

### Clearing a lockout

```
npm run auth:unlock              # every bucket
npm run auth:unlock -- 1.2.3.4   # one address
```

Counters only. `audit_log` is never touched — the record of what happened is the
point.

## Evidence

`evidence/` is regenerated by `npm run test`. Nothing in it is written by hand.

| File                          | What it shows                                                                                                                           |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| `brute-force-1000.txt`        | 1000 failed attempts through the real handler: lockout engaged, 1000 `audit_log` rows, 0 sessions, only 4 guesses ever reached argon2id |
| `set-cookie-headers.txt`      | The verbatim `Set-Cookie` headers, with every required attribute                                                                        |
| `forged-cookie-rejection.txt` | Every single-bit flip across all 207 ciphertext bytes rejected, plus forgery, truncation and post-revocation refusal                    |
| `csrf-rejection.txt`          | Seven ways to get CSRF wrong, all refused, all identically — with the correct password each time                                        |
| `response-timing.txt`         | Wall-clock timing per outcome: 1 ms between medians against an 85 ms internal difference                                                |
| `client-bundle-scan.txt`      | A grep of the built `.next/` output proving no secret reaches the browser                                                               |

## Testing

`tests/auth/` runs against **PGlite** — Postgres itself compiled to WebAssembly
— with `supabase/migrations/*.sql` applied verbatim. The store has exactly one
implementation, so the SQL under test is the SQL that ships. The only stub is
Supabase's own `auth` schema, which the platform provides and this gate does not
use.

The throwaway password in the test suite is not the production one. The
production password appears nowhere in this repository, in any form.
